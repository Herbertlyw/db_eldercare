# 左邻右舍角色工作台修改方案

本方案依据课程任务书第 2.1、2.2、3.4 节和教师讲解中的角色权限、业务留痕要求，设计六种现有账号的工作台首页。目标是让用户登录后看见与自己有关的事项，并直接进入对应业务办理。

六张桌面效果图的整体方向已由项目负责人确认，本轮按此方案在本地实现。图片由 imagegen 生成，图中姓名、金额、日期和数量用于说明布局，不是数据库运行截图或验收结果。实际页面的数据口径与操作说明见 [页面交互与角色操作](页面交互与角色操作.md)。GitHub 发布、课程报告和 PPT 不在本轮范围内。

## 1. 修改范围

本轮设计的页面共六张：老人及家属、护工、社区管理员、机构负责人、街道审核人员、民政监管人员的工作台首页。完整效果图、提示词和浏览入口位于 [页面效果图目录](design/role-workspaces/index.html)。

现有业务列表、详情、操作抽屉和密码弹窗继续使用当前 React / Arco 组件。首页中的“审核预览”是待办记录的上下文预览，最终提交仍通过已有校验及确认流程。既有详情和表单增加必要的上下文跳转及预选，不在本轮重新设计成一套独立页面。若后续需要全面重做这些页面，应另出效果图确认。

不新增用户注册、真实支付、医疗诊断、硬件接入或新账户角色。Java 17、Spring JDBC、MySQL、DDD 风格分层及既有事务边界保持不变。个人材料、课程报告、PPT、Release 不在本轮修改范围内。

## 2. 任务书与页面的对应关系

| 原文依据 | 业务要求 | 页面体现 |
| --- | --- | --- |
| 2.1.1、2.2.1 | 建档、评估、照护计划、评估到期提醒和暂停 | 社区工作台展示复评及计划状态；家属页面可查看评估与计划 |
| 2.1.2、2.2.1—2.2.3 | 下单、推荐护工、接单、改派留痕、服务记录与确认 | 家属预约与确认；管理员派单；护工日程和分状态操作 |
| 2.1.3、2.2.3—2.2.4 | 证书有效期、容量、班次不重叠、有效工时与复核 | 机构排班容量和异常工时；护工查看自己的班次、证书和有效工时 |
| 2.1.4 | 设备历史归属、异常标记、响应期限、升级与处置结果 | 有权限角色展示未完成应急；健康数据保留采样时间与来源 |
| 2.1.5、2.2.1、2.2.5 | 补贴去重、核算追溯、分级审核、抽查公示和整改 | 社区准备材料；街道核验；民政终审、拨付登记和整改复核 |
| 2.2.2 | 老人及家属查看补贴金额与自付部分、提交异常反馈 | 家属费用明细、补贴阶段和反馈入口 |
| 2.2.3 | 护工上报健康异常与居家环境隐患 | 护工工作台保留直接上报入口 |
| 2.2.4 | 招聘、岗前培训、超时未接单、机构考核材料 | 机构工作台分别呈现这些待办及完整业务入口 |
| 3.4、教师讲解约 31:06—32:06 | 不同角色的数据范围；查询视图；监管不得随意修改原始事实 | 所有聚合、详情和按钮沿用服务端授权；证据可核验，历史事实受保护 |

任务书给出五类角色，现有实现将街道与民政细分为两个角色，形成六种账号。工作台沿用这一实现。任务书中的 SQL 举例不直接变成新的统计指标要求；未定义口径的完成率、投诉率不作为装饰性数字加入首页。

## 3. 统一视觉与导航

### 3.1 共用风格

采用白色导航、浅灰页面背景、蓝色主按钮和少量状态色。沿用 Arco 的字体、表单、表格、日期选择器、提示、弹窗和抽屉。卡片以清晰边界和间距区分，避免过多阴影、渐变和大幅装饰图。

桌面参考画布为 1600 × 1000；图片实际像素以生成结果为准。侧栏约 212—240 像素，顶栏约 56—64 像素。主区域按内容分成两栏，信息密集页优先给待办和核验内容足够宽度。页面标题约 24—28 像素，正文约 14—16 像素，表头及关键操作保持可读。

家属和护工页面优先保证文字与操作易读；管理与监管页面使用更紧凑的表格。紧急事件使用红色提示，需关注事项使用橙色；正常业务主要使用蓝色或中性色。状态同时带有文字，不只靠颜色识别。

### 3.2 导航及入口

新增“工作台”作为各角色默认入口。原有业务模块继续可达；图片中的一级菜单是建议分组，不代表删除未展开的查询入口。实施前将现有 `registry.menus` 的每个页面逐项映射到对应分组，确保无遗漏。

页面 URL 区分工作台、业务列表及必要筛选。刷新、浏览器前进后退、返回首页应保持合理上下文。切换用户时清除上一个账号的老人选择、列表缓存和未提交内容。

采用六角色独立首页和常用导航，桌面侧栏宽 232 像素。家属首页保留社区生活照片，其余角色优先展示工作内容。

## 4. 老人及家属工作台

### 4.1 页面结构

1. 标题与老人切换：显示当前有效关联的老人；只有一位时简化选择，多位时明确切换范围。
2. 老人概况：姓名、照片或姓名首字、所属社区、责任护工、当前计划及评估有效期。
3. 下一次服务：预约时间、项目、护工及订单状态。
4. 待确认服务：服务记录提交后，提供查看记录与确认入口。
5. 最近服务：按时间展示已完成及当前需要关注的服务，进入完整记录。
6. 费用与补贴：展示已结算口径的费用，并进入逐笔明细及申报进度。
7. 联系与反馈：服务评价、投诉、异常上报按业务性质区分。

### 4.2 操作规则

- 从首页预约时预选当前老人，后续仍检查有效评估、计划、项目资格与预约时间。
- 确认服务前展示本次服务内容、签到签退、服务记录和护工身份；不在未查看具体记录时直接完成订单。
- “预计可补贴”“已申报”“已审核”“已拨付”明确区分。未核定补贴不能展示为到账金额；已结算费用的订单集合与补贴集合必须一致。
- 有未处理应急时，优先显示相关事件及求助入口，不被普通服务卡片遮住。
- 当前没有关联老人时显示联系社区绑定的说明，不显示其他老人或跨账号缓存。

主要复用 `familyCare`、`elders`、`assessments`、`plans`、`orders`、`waitingConfirmation`、费用查询与 `claimProgress`。以实现中的路由契约为准，所有数据限制在当前有效关联内。

验收重点：多老人切换、取消关联后访问失效、待确认到已完成的变化、补贴阶段文案、空数据和加载失败。

## 5. 护工工作台

### 5.1 页面结构

以日程为主体，顶部显示日期、今日安排、待接单及本月有效工时。任务按服务时间排列，一条任务呈现老人、项目、地址、时段、状态和当前可执行动作。

“今日安排”与“待接单”分开；未完成的历史任务单独提示。右侧展示自己的班次与容量、证书提醒、健康异常及居家隐患上报入口。查看其他日期不会隐藏应急事项。

### 5.2 状态与动作

| 业务状态 | 页面操作 |
| --- | --- |
| 待接单 | 查看详情、接单；按既有规则办理退单 |
| 已接单且待上门 | 查看服务要求、到达签到 |
| 服务中 | 查看已记录信息、提交必要记录、按规则签退 |
| 已签退但记录不完整 | 补充本人有权填写的服务记录 |
| 待家属确认 | 查看已提交记录和等待状态，不代替家属确认 |
| 已完成 | 查看历史服务，不修改终态事实 |

具体动作顺序以现有服务状态机和后端接口校验为准，效果图上的按钮不是绕过检查的快捷路径。证书过期、请假、容量不足、整改限制等情形应说明原因。

主要复用 `orders`、`shifts`、`hours`、`monthlyHours`、`credentials`、`trainingRecords` 及应急相关入口。日程排序须由后端保证；不能取通用列表第一页后排序，冒充完整日程。

验收重点：跨日任务、昨天未完成事项、待接单不限于今天、签到签退边界、自己的历史订单可查但不扩展为全部老人档案权限。

## 6. 社区管理员工作台

### 6.1 页面结构

优先展示需响应的应急和逾期事项，其次是服务调度、评估与计划、投诉待受理、补贴材料准备。建档作为明确的主操作，老人迁移在档案业务中保留完整入口。

服务调度区区分待派单与超时未接单；评估区区分即将到期与已过期；补贴区列出符合条件订单和材料准备入口，而不是只显示申报总数。

### 6.2 办理衔接

- 从待派单进入推荐结果，保留订单和老人上下文；核对服务区域、资质、可服务时段及班次容量。
- 无候选时解释限制原因，不给出不可用的空选择框。
- 改派必须填写原因，并可查看原派单记录。
- 复评后按现有规则处理计划衔接，不自动将暂停计划视为恢复生效。
- 补贴申报保留按周期、项目与老人核算的规则，以及证明材料归档入口。

主要复用 `dispatchPool`、`assessmentDue`、`activePlans`、`pendingEvents`、`complaints`、`eligibleClaims` 等授权查询。首页显示本社区范围。

验收重点：从首页进入办理后无需重新寻找记录，办理成功后当前待办消失或更新；不同社区管理员不可通过更换参数访问对方数据。

## 7. 机构负责人工作台

页面以人员资源和执行问题为中心：今日或指定日期的排班与容量、证书到期、异常工时、超时未接单、待回复投诉和整改。招聘、岗前培训与机构考核材料保留显著入口。

- 排班显示“已接 / 容量”，同时展示请假、停用等状态；时间冲突和容量规则由后端校验。
- 异常工时复核展示签到签退、围栏结果与复核依据，不让负责人随意重写原始时间。
- 机构超时订单用于查看并跟进本机构任务；具体改派仍按现有授权由社区管理员办理。
- 整改展示要求、截止时间、已提交材料及退回意见。
- 机构考核按当前材料状态提供填写、提交和查看意见入口。

主要复用 `shiftCapacity`、`credentialDue`、`hoursReview`、`managerDispatchPool`、招聘培训、投诉、整改和 `organizationReports` 等查询。不得扩展为其他机构的护工资料。

验收重点：机构范围、状态与可操作按钮一致、证书与培训分别展示、审核历史和原始工时不被覆盖。

## 8. 街道审核工作台

采用待审列表与核验预览并列的布局。选择一份申报后展示老人、社区、周期、政策、金额、关联订单和材料。审核意见与动作位于核验内容之后，避免先点通过再补看证据。

核验至少包括：订单集合、订单完成状态、有效工时、服务记录、老人或家属确认、政策条件、材料和已有审核记录。确认记录、工时和材料可点击查看；不提供编辑原始服务事实的操作。

- 只允许当前授权社区中符合初审状态的申报进入审核。
- 退回需填写补正原因；通过也沿用既有审核意见及事务校验。
- 申报状态被其他人员处理后，提示刷新并保留未提交的意见供用户判断；不得悄悄重复提交。
- 辖区服务统计、补贴政策和质量公示继续提供查询入口。

主要复用 `claims`、`claimProgress`、申报详情中的“订单与核算依据”、申报材料和审核历史，沿用 `account_scope`。图中的勾选提示仅代表真实核验结果，加载失败或未查到数据不能显示“齐全”。

验收重点：初审与终审权限分离、证明材料可追溯、退回原因必填、跨社区拒绝和并发状态变化。

## 9. 民政监管工作台

页面同时呈现辖区概览与监管待办。概览仅使用已有且口径明确的覆盖率、及时响应率等指标；清楚标注统计月份、授权范围和分子分母，能够进入明细核对。

待办包含补贴终审、拨付登记、比例抽查、整改复核、公示和机构材料审核。各类待办分开呈现，避免用同一个“审核通过”按钮混合不同业务。

- 终审展示街道初审意见与原始核算依据。
- 拨付操作登记凭证和结果，不表示系统接入银行转账。
- 抽查保留比例、抽查总体及抽中对象的可追溯信息。
- 整改复核可查看整改要求、提交材料和处理历史。
- 监管人员核验事实、作出审核和整改意见，不任意修改原始服务时长、记录或补贴凭证。
- 切换社区只允许选择授权范围；汇总范围与明细范围保持一致。

验收重点：统计分母为零、不同账号授权范围、终审与拨付状态、抽查比例及整改未完成的接单限制。

## 10. 共用交互规则

1. 从老人、订单、申报或整改卡片进入办理时携带具体记录编号，预选可确认的字段，并清楚显示当前对象。
2. 返回列表保留筛选、日期与页码；成功提交后刷新受影响的待办和关联数据。
3. 未提交内容离开前提示；网络失败保留当前输入，不自动重试会写入业务的请求。
4. 加载中显示占位；空结果显示正常的空状态；失败显示错误及重试入口。三者不能都显示为“0”。
5. 首页可以减少按钮，但不能增加角色权限或取消服务端约束。每项写操作仍经过 `CareService.execute` 的事务入口。
6. 健康数据展示采样时间、来源及异常状态；异常提示不写成自动医疗诊断。
7. 名称和照片使用现有资料；无照片采用姓名首字，不能借用其他人的头像。效果图中的新人物照片不自动替换当前资产。
8. 超时与应急状态以服务端时间和状态为准。刷新、后台标签页、多个窗口与不同机器时间偏差均需测试。

## 11. 实施结构与接口检查

### 11.1 前端

建议在 `frontend/src/pages/workspaces/` 下建立六个角色工作台组件，通过明确的角色映射选择页面。`Workspace` 保留共用壳体及业务列表入口；不要把六套逻辑挤进一个越来越长的角色条件分支。

共用组件仅抽取真实重复部分：待办行、时间安排、统计值、加载/错误/空状态和关联记录入口。页面特色通过组合组件表达，不复制六套表单、详情或权限判断。

`registry.json` 继续维护业务能力和完整菜单。新一级导航分组需映射现有菜单；`rules.ts`、`schema.ts` 的状态及字段规则继续复用。工作台不能维护一套独立且容易失配的业务状态机。

### 11.2 后端和 SQL

先检查现有读接口是否足够表达所需内容。组合状态、服务时间排序、统计汇总或按老人聚合不足时，再增加明确的只读查询及返回类型。不能通过取全部记录后在浏览器筛选，替代服务端分页和授权。

查询需声明时间范围、排序方式、状态集合、数据范围和空集规则。现有通用分页按编号排序，护工日程需要单独满足按服务时间稳定排序的要求。费用与补贴必须使用同一订单集合及明确的结算状态。

后端继续通过授权接口和 JDBC 查询实现；新增查询维护路由契约。金额核算、服务完成、容量、有效期、历史保护和数据库事务规则不因首页变化而修改。

### 11.3 数据来源清单

实施前为每个首页区块记录：显示字段、数据来源、角色范围、筛选与排序、点击目标、刷新条件。对于当前接口无法直接提供的组合数据，先补查询设计，不在页面中写固定数字。

本方案不要求建立新业务表。若实施发现需要保存新的用户偏好或草稿，另行确认存储范围、有效期及账号隔离，不将这类可选功能夹带进首页改版。

## 12. 响应式与可访问性

桌面采用两栏或核验分栏；中等宽度时辅助区下移；手机端使用单列，优先呈现应急、下一件任务和主要操作。审核页面在手机端先展示申报列表，进入单份记录后展示依据和审核操作，不强行挤成左右两列。

键盘可访问导航、日期选择、任务、按钮和弹窗。焦点顺序与视觉顺序一致，返回时恢复合理焦点。表格操作不依赖鼠标悬停；截断文本可查看完整内容。大字号情况下不遮挡按钮。照片仅为辅助信息。

手机端按上述规则适配，以实际浏览器页面供项目负责人查看。

## 13. 实施顺序和验收

| 阶段 | 交付内容 | 验收重点 |
| --- | --- | --- |
| 设计确认 | 六张图片、页面职责和入口映射 | 信息顺序、字号、密度、每个角色的工作重点 |
| 共用入口 | 工作台路由、导航、角色选择、异常状态 | 登录默认入口、刷新与返回、无遗漏菜单 |
| 家属与护工 | 照护概况、预约确认、日程与服务动作 | 同一订单能跨角色正确流转 |
| 社区与机构 | 调度、复评、工时、招聘培训和整改材料 | 原有约束、权限与处理历史保持完整 |
| 街道与民政 | 核验预览、分级审核、统计与质量监管 | 证据可追溯、金额一致、原始事实不可随意改写 |
| 全面验证 | 六角色、跨社区/机构、手机及异常路径 | Java/MySQL、前端规则和浏览器检查分别留证 |

核心验收使用同一老人的一条业务线：建档与评估 → 计划 → 预约 → 派单 → 护工服务 → 家属确认 → 补贴申报 → 街道初审 → 民政终审及拨付登记；另验证招聘培训、投诉结案、比例抽查、整改复核公示、应急响应与升级。

异常测试覆盖评估/证书过期、排班冲突和容量不足、超时未接单、异常工时、未确认服务、补贴重复申报、整改限制接单、权限变化、重复点击和并发状态变化。检查正常流转，也检查拒绝操作后数据库没有留下部分写入。

页面至少验证 390、768、1280、1600 像素宽度，检查长姓名、长地址、零待办、无关联老人、数据加载失败和会话失效。需要真实 MySQL 集成测试；浏览器写入验证使用独立测试库，关闭调度；定时任务单独验证。展示库不重建。

每次测试只报告实际执行的范围。图片确认不等于代码验收，代码测试通过也不代替用户对页面的视觉确认。

## 14. 设计选择与本地预览

家属首页保留生活照片；护工默认当日安排，可切换待接单；街道采用左右核验布局，窄屏上下排列；监管页按授权范围展示统计与待办。页面的视觉细节以本地预览反馈为准。
