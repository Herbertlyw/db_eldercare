# 运行维护与验收

## 环境和边界

Java 17、Spring Boot 3.4.4、Spring JDBC，真实 MySQL 8.4.11。本机独立实例绑定 127.0.0.1:33316，应用绑定 127.0.0.1:18080。Windows 使用安装好的 Java 和 MySQL，通过配置更换 JDBC 地址，Docker 不参与运行。

【待确认】Windows 脚本需要在目标电脑执行，补充初始化、启动和业务操作结果。

设备上传和地理围栏为课程模拟。指标上下限、设备规则配置的初始响应时限、人工事件按级别采用 300/180/60 秒、升级后按级别采用 180/60 秒及每次 30 元补贴均为演示配置，不能用于真实医疗或财政业务。补贴按政策选择月、季或年结算，同一老人同一项目的申报周期不得重叠。驳回后在原申报补充材料并重新提交，原订单明细与历次审核不删除。

## 过程与触发器对应

| 业务线 | 过程 | 触发器与作用 |
| --- | --- | --- |
| 档案与评估 | expire_plans | plan_before_insert / update 调用 assert_plan 检查评估和计划重叠 |
| 下单与派单 | assign_order | order_before_insert 检查有效照护，order_before_update 检查确认凭据和完成后不可改 |
| 护工与排班 | verify_hours | shift_before_insert / update 检查重叠班次；CHECK 保护容量范围 |
| 监测与应急 | escalate_events | vital_before_insert 校验绑定时刻和阈值，vital_after_insert 建待确认事件 |
| 补贴与监管 | submit_claim | claim_before_update 保护审核流转、明细金额与已拨付记录 |

过程由 Java 事务调用，过程内部不 COMMIT；一个业务方法失败时统一回滚，不能在调用链中提前提交。定时任务每 30 秒检查到期和超时，属于应用进程内调度，进程停止后暂停，恢复后补处理。重要入口还会即时校验有效期，不能只依赖定时状态更新。

## 索引方案

1. idx_assessment_elder(elder_id,valid_until)：按老人查有效评估，适用于资格判断和复评清单。纯到期全库扫描可能仍需时间列开头的索引，应根据实际规模再决定。
2. idx_plan_assessment(assessment_id,status,starts_at,ends_at)：关联评估并筛选计划。重叠判断仍需比较结束时刻，不能把索引等同于区间约束。
3. idx_order_status_time(status,starts_at)：调度状态与预约区间查询。证据中对比忽略该索引与使用该索引的 EXPLAIN；当前数据量较小，性能结论需用更大数据集验证。
4. idx_order_elder(elder_id,starts_at)：老人订单分页、历史服务和月度申报筛选。
5. idx_shift_caregiver(caregiver_id,starts_at,ends_at)：查护工时段及候选班次。
6. idx_emergency_deadline(status,deadline)：定时筛选未响应且超时的应急事件。
7. idx_audit_object(table_name,row_id)：追溯指定业务记录的状态历史。

多对多表使用组合 UNIQUE 防止重复关系。生成唯一列 active_order 和 active_device 分别保证一单只有一个有效派单、一设备只有一个当前绑定。外键自动或显式建立必要访问索引，避免对每个字段机械加索引。

## 登录和敏感字段

密码以 BCrypt 12 轮加盐摘要保存。连续失败 5 次后锁定 15 分钟，失败计数使用独立数据库事务提交，避免抛出登录错误时把计数一起回滚。会话由服务端保存随机令牌，固定 30 分钟到期，退出立即删除，应用重启使既有会话失效。每次请求重新检查账户状态和授权范围，账号停用、角色或归属社区变更后旧令牌失效；多社区授权范围的修改在下一次查询时生效。当前是单实例课程实现，未做分布式会话共享。

身份字段以 AES GCM 加密，用 HMAC SHA-256 支持唯一查重；当前示例共用一份应用字段密钥分别调用加密与 HMAC，生产应实施独立密钥、轮换与外部密钥管理。密钥只保存在本机 .local 配置中，不进入版本库或分发包。档案查询不返回身份密文、查重摘要或密码摘要。

所有用户值通过 JDBC 参数绑定。可选数据类别与存储过程名使用固定白名单，不能将用户传入的表名或 SQL 直接执行。角色权限在业务入口检查，家属关系、护工订单及机构辖区再决定行范围。服务仅绑定本机回环地址，若改为远程访问需增加 HTTPS 和部署侧访问限制。

## 备份与恢复

【待确认】备份方案暂定为每日全量备份，每 15 分钟复制新增 binlog，保留最近 7 天。目标恢复点为 15 分钟以内，目标恢复时间为 30 分钟。目前尚未设置长期定时任务，也未测量这两个目标，需在实际部署时验证。

全量使用 mysqldump --single-transaction --source-data=2 --routines --triggers --events，保存结构、数据和例程。备份期间避免 DDL，记录与一致性快照对应的日志位置。实际部署应采用 dump 的日志位置信息或受控写入暂停来衔接全量与增量；不能随便把完成导出后的任意日志位置作为起点。演练脚本在受控课程实例上执行，演示单条事务的日志恢复，不等于覆盖所有生产故障。

恢复步骤：停止目标业务写入；在独立空库导入全量；按开始和结束日志位置重放 binlog；核对各基础表行数、外键和例程，再运行核心查询及业务拒绝测试；确认后再切换业务连接。禁止直接在未知的已有数据库中覆盖恢复。

实际证据见 evidence/recovery.json：全量恢复后重放一条真实的新增服务项目事务，并逐行比较 47 张基础表的内容，再执行恢复库中的 15 组查询对比。日志起点取自全量备份内的一致性快照坐标。备份文件在 .local/backups，防止把含账号摘要和字段密文的数据随源码公开。

## 已遇到的问题与处理

1. 本机 Homebrew MySQL 的动态链接库缺失，Docker 内部磁盘也已满。最终复用可工作的 MySQL 8.4 程序，以独立数据目录和端口启动原生实例，不改动原实验数据库。
2. 初始表结构重复保存了计划所属老人和派单所属护工。根据函数依赖拆除重复字段，通过两个内部视图还原查询上下文，迁移时保留业务记录，然后重跑数据库集成测试。
3. 完整流程测试暴露了 JDBC 日期类型差异和直接访问被代理 DAO 字段的问题。分别统一时间对象处理、将访问封装回 DAO 方法，增加完整服务确认与工时复核的回归测试。

## 本次需求与代码复查

派单、接单和签到共用资格检查。除有效评估外，还检查护工在岗、账号启用、证书覆盖服务时段、区域、班次和整改。推荐结果只供选择，真正派单时仍在事务锁内重新核验。按小时计费时，订单价格按标准分钟数折算。

超时调度池由视图自动列出创建超过 15 分钟的待派订单，以及当前派单超过 15 分钟仍未接单的订单。界面提供查询和人工改派。评估到期提醒、异常工时、可申报订单等 15 个业务视图均接入有权限限制的查询入口。

设备绑定使用微秒时间，禁止改写历史老人归属和重叠绑定区间；解绑不能切断已有采样的有效区间。新应急事件立即产生家属、责任护工和社区的站内通知，超时升级后再次通知，人工上报保留在事件日志中。未接入短信或电话网关。

工时汇总按签到月份统计有效分钟。护工评价分别展示家属的 5 分制评分和抽查的 100 分制评分，机构评价汇总所属护工及其已完成订单的抽查结果，不虚构综合评分权重。

监管账号通过 account_scope 关联多个社区；街道和民政分别使用各自授权集合。辖区统计按当前在册老人计算本月服务覆盖率，按非误报且保存首次截止时间的本月事件计算及时响应率。老人归属采用当前社区；已申报和已拨付金额按申报快照中的社区汇总。分母为零时显示“—”，不显示虚假的 100%。迁移前缺少首次时限的旧事件不倒推补填。

## 新增流程的验收口径

招聘分登记、录用或拒绝；录用建立护工账号和默认服务区域。培训单独安排、登记参训和成绩，结束后才能登记分数；课程配置为 60 分通过。派单同时检查已通过的培训与有效项目证书，两者不能相互替代。

服务评价与投诉分开处理。评价要求订单已完成；投诉依次为提交、社区受理、机构或社区回复和家属或社区结案。办理记录只追加，每一步保存经办账号和说明。家属能够查看订单的服务内容、实际护工、工时与确认凭据。

社区服务范围和围栏采用虚构平面坐标，单位为米；住址不能超出所属社区半径，订单保存下单时的坐标。签到和签退均由服务端计算距离，不接收客户端直接指定“通过”。围栏或预约时段异常、实际服务不足预约时长 80% 的工时进入复核；核准零分钟服务被拒绝。80%、前后 30 分钟及围栏半径均为课程演示规则，不是任务书给定的行业标准。

每台设备由管理员明确开启定时模拟采样，间隔为 30—3600 秒，默认关闭。任务每 30 秒检查到期设备，在当前绑定下生成正常范围模拟值，记录上次采样时间；异常值由批量上传入口演示。设备离线、停用或解绑时不生成定时样本。通知为站内记录，不接入真实短信或硬件。

监管人员按社区、服务期间及对象类别建立抽查批次。系统对符合条件的已完成订单或其护工排序抽样，样本数为总体乘比例后向上取整。批次保留范围、总体数、种子及实际抽中记录；历史抽中记录不变，之后新增的服务记录不会自动加入旧批次。低于 60 分或明确要求整改的检查进入整改流程。机构可提交材料，监管可通过或退回；退回后保留旧材料并追加新提交。公示仅包含方式、评分和完成状态，隐去身份、地址和健康、投诉明细。
