### 不能仅凭测试数量判断完成的部分

1. **数据库约束和原始事实保护仍有边界。**已确认服务、已完成订单、体征、申报明细、拨付等已有保护。但应用数据库账号仍能直接修改已认定工时分钟数、历史评估分数。本轮使用 elder_app 在 eldercare_test 验证了两次 UPDATE，均成功后 ROLLBACK；不是使用 root 绕过权限。普通网页角色没有任意 SQL 入口，不能据此说家属能直接改工时；它说明数据库层的历史保护不完整。S2 06:51、18:58 强调留痕，应补受控修正与必要旧值记录，而不承诺防住最高权限 DBA。
2. **两种 SQL 结果相同，不保证业务口径正确。**A1、A3 用 ACTIVE 判断有效计划，未同时检查计划起止时刻；未来开始但状态为 ACTIVE 的计划会被当作当前有效。v_family_care 也只按状态连接；评估提醒没有排除已被复评替代的旧记录。需要补时间边界和业务期望值测试。
3. **现有数据覆盖不足。**每张表至少 20 条这一数量要求已有证据，但当前 assessment、care_bundle、policy 各 20 条全为 SEVERE，缺少自理/部分失能的完整可演示配置。不能将“枚举写了三种等级”当作三种老人都能从页面走完流程。设备与指标也是通用模拟名称，仍应补有区分的演示案例。
4. **基础资料管理不能永远依赖种子数据。**账号、护工、服务区域、服务项目、服务包明细、阈值、政策的维护入口尚不齐全。任务书不要求所有表都做机械式增删改查，但五类角色必须能完成其明确业务；缺少这些入口会使演示局限于预置数据。
5. **设计材料也未覆盖全部要求。**现有用例、鲁棒图和实体模型描述的是已经实现的子集，招聘培训、投诉处理过程、比例抽查、公示、辖区授权等还需在补做后同步到模型、字典、SQL、测试、报告和 PPT。已有图数量及排版合格不能代替需求完整。

### 尚待确定的异常流程，不伪装成任务书原句

<span style="color:#1565C0">补贴驳回后修改重报、护工明确拒接、投诉重新打开、计划频次是否作为强制预约上限、过短工时判定阈值、具体覆盖率分母、跨月工时如何分摊，都应在实现前说明业务口径。当前补贴一旦驳回，没有重报入口，唯一约束也会阻止直接新建同月同项目申报；这是实际流程限制，但原文没有单列“必须支持重报”的条款。应保留旧审核历史来完善，不能删除旧申报绕过约束。</span>

## 本次发现并修正的问题

第一轮新增 12 个检查，其中 11 个在原代码上失败或报错。这些失败来自真实 MySQL 和 HTTP 测试，记录在本次复查的测试源代码中。

1. 按小时收费的项目直接使用单价，90 分钟仍收一小时费用。改为按标准分钟折算并保留两位小数。
2. 接单只复查证书，签到未重新核验资格。统一派单、接单和签到检查，并在数据库接受派单时再检查，阻止请假、证书过期、评估失效或整改中的护工继续承接。
3. 调度池只包含待派单，遗漏已派出但迟迟不接单的记录。增加当前派单超过 15 分钟的自动筛选。
4. 应急消息仅在定时检查时发给管理人员。补充立即通知家属、责任护工和社区，增加人工与家属上报，按级别确定后续响应时限。
5. 设备绑定可改写老人编号，旧数据归属因此改变；已关闭区间也可相互重叠。增加历史不可改和区间约束，并用微秒时间支持连续换绑。
6. 停用账户后旧会话仍能使用。每次请求重新核验账户和权限，账户停用或授权变更立即使旧令牌失效。
