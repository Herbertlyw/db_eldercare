# 左邻右舍 · 项目问题与修复记录

截至 2026 年 11 月 18 日。本文汇总开发会话、Git 提交和本地验收记录中能核实的问题。每项从使用者遇到的现象或源码里的具体风险写起，列出处理方式和回查依据。同一问题历经几次修改的，放在一处说明。

## 一、11 月 18 日桌面版修复

这一轮有两个事务并发风险，两个实际看见的业务问题，以及四项工时和页面改进。验收对象为本地 `codex/role-interactions` 工作区，基线提交为 `57b731e`，本节改动尚未提交。

| 问题 | 处理方式 | 怎样验证 |
| --- | --- | --- |
| **护工签到与退回调度抢同一单。** 两边都先读订单再等锁，后取得锁的一方可能拿着旧状态释放名额。源码复查发现了这条路径，当时没有观察到真实订单损坏。 | 签到和退回都先锁定订单，再按当前状态复核本单是否仍可办理。 | 真实 MySQL 双连接让退回请求实际等待签到事务。签到先成功后，退回被拒，订单仍在服务中，只有一条签到记录，班次名额仍被占用。 |
| **同一份整改可能收到相反的复核决定。** 第二位复核人更新到零份待审材料，仍可能把抽查主表写为退回。起初同样是源码发现的风险。 | 在锁内读取抽查状态。复核必须实际处理一份待审材料，才能更新主表并记录复核决定。 | 两个连接分别提交通过和退回，只留下先完成的决定。另测缺少待审材料，复核被拒，主表保持待复核。 |
| **已按时响应的应急被标成超时。** 展示库 28 号事件早已响应，民政首页仍显示“已超过当前响应期限”。 | 先看是否响应、是否到场，再决定显示倒计时、响应超时、待到场或待结案。及时响应率继续按首次截止时间计算。 | 桌面实查 28 号事件显示“已响应，待到场”，并核对未响应超时的事件。 |
| **错过整个预约时段的订单仍可尝试派单。** 初查时青禾社区 16 笔待派订单里有 8 笔已过预约结束时间。 | 社区将过期订单列为“待联系”，关闭原时段的推荐与派单。联系家属后可在原单上改约并重验计划，或由管理员取消。等候接单超过 15 分钟、预约时段仍有效的单继续调度。 | 独立库验证过期单保留、过期派单被拒、有效改约回到待派队列。展示库升级派单过程前后，47 张基础表行数一致。验收时待联系数为 9，数量随时间变化。 |
| **服务工时最初只列打卡明细，后来有了合计，但浏览器每 100 条翻一页才算得出。** | 护工、机构负责人、社区管理员各自在授权范围内查看汇总。MySQL 使用与明细相同的筛选条件汇总有效分钟和各状态数量。只有有效工时计入合计，翻页只读取该页明细。 | 数据库专项造了 106 条记录，其中 102 条有效，每条 5 分钟。三个角色在同一范围内查看首页和末页，汇总都是 510 分钟，换成无权查看这些记录的账号时为 0。桌面核对三个角色。之前的浏览器夹具还验证过 105 条各一分钟，翻页后仍是 1 小时 45 分。 |
| **同一护工跨月时，月工时的两行使用同一个行标识。** SQL 按人、月分组，界面却只用护工号标识。 | 以护工编号和月份共同标识记录，先按月份倒序、再按护工编号排列。 | 前端单测验证同一护工在两个不同月份的行标识不同，排序规则核对了查询源码。[行标识用例](../frontend/tests/workforce.test.ts) · [月工时查询](../src/main/java/edu/bjfu/eldercare/infrastructure/query/WorkforceQueries.java) |
| **家属预约重复询问已确定的信息。** 从“预约上门服务”进入，还要选业务类型、确认唯一渠道，并看到两次选时间提示。 | 依序核对老人、选择时间、选择可预约项目。家属渠道自动带入，更换老人或时间会重新核对项目。 | 桌面浏览器断言只出现老人、时间、项目三个业务字段，时间提示仅出现一次，并在独立库完成预约提交。 |
| **护工当天没有安排时，日程、班次、遗留任务各显示一张空卡。** | 三部分均成功加载且都为空时合成一条提示，保留切换日期和上报异常入口。加载失败仍可重试。 | 桌面浏览器检查当日空日程只出现一条提示，切到“待接单”后这条提示消失。日期切换与加载失败重试另有工作台专项检查。 |

本轮 199 项 Maven 测试、30 项前端单元测试全部通过。现存 13 份 Surefire 套件报告合计 199 项，失败、错误、跳过均为 0，含真实 MySQL 集成、领域规则等检查。业务写入在独立库验证。可回查[五个 MySQL 专项用例](../src/test/java/edu/bjfu/eldercare/ReviewConsistencyIntegrationTest.java)、[派单过程升级脚本](../database/migrations/20261118_dispatch_window.sql)和[当天的原始发现及桌面验收](项目复查-20261118.md)。

## 二、五条业务线中补齐的流程与修复

本节主要对应 11 月 12–16 日。第一轮专项检查增加了 12 个用例，其中 11 个在修复前失败或报错。随后又按任务书及教师讲解重走整条业务线，发现了“数据已存、对应角色却办不了或看不到”的缺口。以下记录把这些情况与计算、事务和授权错误分别写明。[任务书核对底稿](../evidence/requirements-gap-audit.json) · [按业务列出的入口与测试方法](功能验收清单.md)

### A　老人档案、评估与照护计划

| 当时的问题 | 修复与验证 |
| --- | --- |
| 身份号前后空白或字母大小写不同可能绕过查重。档案能建立，但标签、家属关系和联系方式缺少维护入口。 | 查重前统一身份号格式。补齐标签、关系及加密联系方式维护，停用家属关联后立即失去关联档案的访问权。测试包含重复身份、跨范围访问、停用关联和加密存储。 |
| 计划能新建，却不能完整修订、终止，家属也看不到项目及频次。部分“当前计划”查询会提前列出尚未生效的计划。 | 修订保留旧版本、服务项目和频次，可暂停、恢复或终止。当前计划同时校验状态、起止时间和评估有效期。回归覆盖历史明细、未来计划及并发创建重叠计划。 |
| 复评后，旧评估仍可能进入提醒清单。探索用例还观察到，老人复评为自理后仍能按原重度失能计划下单，补贴核算却依据较新的评估。 | 到期提醒只看最新已生效评估并去重。按项目约定，当前复评暂停旧计划，新服务依据最新评估办理，已完成订单与已拨补贴保留原记录。测试分别检查新计划和历史服务。 |
| 老人迁到新社区时，原社区的设备、未完成订单和既有服务归属容易混在一起。 | 项目约定先处理未完成订单、解绑原设备，再办理迁移。设备留在原社区，历史采样保留原绑定，迁入后可绑定当地设备。回归覆盖被拒时零变更和成功迁移两条路径。 |

评估、计划、迁移分别有授权、时序和历史用例。复评暂停旧计划、迁移前解绑属于项目选定的业务规则。[历史规则复查与验证](../evidence/history-fix-verification.json) · [迁移和复评的浏览器记录](../evidence/history-browser.json)

### B　预约、派单、服务确认与投诉

| 当时的问题 | 修复与验证 |
| --- | --- |
| 按小时计价直接取单价，90 分钟的服务只收一小时。 | 按标准服务分钟数折算金额，保留两位小数。价格用例覆盖 90 分钟和按次收费。 |
| 下单渠道缺电话代订，地址校验只比较社区编号。 | 补齐家属、社区和电话渠道，服务端检查地址坐标是否在服务范围内并保存当次订单地址快照。覆盖范围外地址和地址后续变动。 |
| 派单时合格的护工，在接单、签到前可能已请假、证书过期或处于整改中。派出后迟迟未接的单也进不了调度池。 | 推荐、派单、接单和签到按相应时点核验资格。超过 15 分钟未接的派单进入调度池，支持护工拒接和机构退回，保留原因并释放名额。回归另覆盖最后一个名额、同一护工重叠预约和改派失败回滚。错过整个预约时段的处理见第一节。 |
| 机构只要服务过某位老人，就能读到该老人其他机构的订单。 | 按每一笔订单的派单关系检查机构权限。用同一老人、不同机构的订单验证能看和应拒的两种结果。 |
| 家属能点确认，却难以先核对实际护工、服务内容及过程，完成订单时的家属身份校验也不充分。 | 订单详情提供服务记录、打卡和确认依据。服务完成按工时审核、授权家属确认推进，检查冒用身份、跳过确认及正常完成。 |
| 终态派单可以被直接 SQL 改写，可能丢失退单或改派历史。 | 在数据库保护完成、拒接和已改派等终态记录，以及已确立的派单、接单时间。直接更新被拒，正常改派、取消和失败回滚仍能执行。 |
| 提交投诉后缺受理、回复、进度和结案。未派单投诉没有所属机构，很难找到承办人。 | 普通评价与投诉分入口。投诉由社区受理、自办或转机构，回复、确认结案和历次处理可查，处理记录只追加。浏览器走通提交至结案，另测未派单投诉由社区办理。 |
| 护工服务均分把投诉记录的评分也算了进去。一次只读样例中，仅评价为 4.50 分，混算为 3.17 分。 | 聚合只计普通评价 `REVIEW`，没有评价时返回空值。验证混合记录、无评价及角色范围。投诉率另有定义，不从这个均分推算。 |

依据包括[早期代码专项检查](../evidence/code-audit-20261112.json)、[历史保护迁移](../database/migrations/20261113_history_rules.sql)、[业务流程回归](../evidence/completion-browser.json)和[证书及评分专项验收](../evidence/acceptance-summary.json)。

## 三、账号、数据、代码与运行

| 问题 | 处理方式与回查依据 |
| --- | --- |
| 登录失败后抛出异常，失败次数随业务事务回滚，锁定规则失去依据。账号停用或授权变化后，旧会话还可能继续访问。 | 用独立事务保存失败次数，请求重新核对账号及权限。回归包含失败次数持久化、停用、撤销和访问范围。[数据库集成测试](../evidence/TEST-edu.bjfu.eldercare.DatabaseIntegrationTest.xml) |

## 七、审查中澄清的判断与尚未验收的事项

- **任务书举例和必做功能。** 招聘培训、投诉结案、按比例抽查、公示和跨社区监管有任务书依据。月度完成率、投诉率、重度失能查询是复杂查询举例。评价均分混算需要修，另做投诉率报表属于不同工作。A1 示例 SQL 未列社区和责任护工，当前有效计划的授权查询已能按社区过滤并带责任护工。15 组查询用两种写法比较，结果一致是预期的验证结果。[课程条款对照](需求追踪与模板差异.md) · [11 月 18 日复查](项目复查-20261118.md)
