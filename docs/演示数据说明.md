# 演示数据说明

平台使用虚构的老人、服务记录、政策和监测数据。业务示例集中在青禾、桂园社区，供管理员、家属、护工、机构负责人、街道和监管人员演示完整业务。服务时间按首次导入日期安排，已导入的记录保留实际时间，不随每次启动自动刷新。

## 示例内容

| 业务 | 数据内容 |
| --- | --- |
| 档案与照护 | 周惠琴、何德明等 7 位老人，含一份停用档案；三种能力等级，独居、失能、低保标签；正常、暂停、到期、终止计划，近期到期的评估 |
| 服务项目 | 午间送餐、居家清洁、陪诊、助浴、陪伴、康复协助；按次和按小时计费，含可补贴与不补贴项目 |
| 订单与工时 | 电话、家属、社区三种预约来源；待派单至完成的各阶段、取消、退单与改派历史；正常工时、服务中打卡、待复核和无效工时 |
| 招聘与培训 | 待审查、录用和拒绝录用；在岗、请假、离职；待培训、通过、未通过；不同项目资质及近期到期证书 |
| 评价与投诉 | 不同评分的服务评价；待受理、已受理、已回复、已结案投诉，并有受理、回复和回访记录 |
| 设备与健康 | 腕式设备、血压计、血氧仪；正常、离线、停用；有效绑定和解绑历史，正常及异常采样；定时采样开关的两种配置 |
| 应急 | 设备、人工、家属求助三种来源；三级事件；待核实、待响应、已响应、结案、误报；响应、到场及结案记录，含超时响应样例 |
| 补贴 | 月度、季度、年度政策，不同能力和标签条件；草稿、提交、街道通过、监管通过、驳回、拨付；按次与按工时核算，街道和监管两个环节的驳回意见 |
| 质量监管 | 电话和上门抽查，订单和护工两种对象；待抽查、待整改、待复核、结案；整改待审、通过、退回；机构材料待审核、采纳、退回，以及公开、撤回的公示 |

已完成订单保留派单、打卡、服务记录和家属确认。补贴明细关联已完成且工时有效的订单，核算由数据库过程执行，拨付金额与申报金额一致。草稿是尚未提交的材料准备示例，金额为零；提交、审核和拨付样例各自保留相应证据。

未完成的订单、投诉、工时复核和应急事件可以继续通过页面办理。部分护工有待整改记录，其继续接单会受到业务规则限制。离职账号停用；停用设备已解绑。未配置照片的档案显示姓名首字，不借用其他人的照片。

| 账号 | 可查看的示例 |
| --- | --- |
| `admin1`、`admin2` | 各自社区的档案、订单、设备、应急及补贴 |
| `family1`、`family2` | 各自关联的老人、服务进度、反馈及补贴 |
| `scene_caregiver1` | 沈丽萍的服务订单、班次、资质和待接单任务 |
| `scene_caregiver2` | 邱志强的服务记录及整改关联情况 |
| `scene_caregiver3` | 吴晓梅，请假状态，包含未通过复训与将到期证书 |
| `scene_caregiver5` | 叶春华，桂园社区服务记录 |
| `manager1` | 招聘、培训、护工、工时复核、投诉及机构材料 |
| `street1`、`regulator1` | 授权辖区内的补贴、抽查和社区统计 |

新护工账号的初始密码与导入时 `family1` 的密码相同，使用相同的 BCrypt 存储方式。`scene_caregiver4` 对应离职人员，不能登录。其余原有账号与密码保持不变。

家属只能访问关联老人。社区管理员不能查看其他社区的业务详情；街道和监管人员按 `account_scope` 中的授权查看跨社区业务。监管汇总和补贴核验权限不等于查看完整个人档案的权限。

## 导入与维护

1. 按 README 准备 Java 17、MySQL、数据库连接和字段加密密钥，完成基础种子初始化。
2. 停止连接目标库的应用，备份目标库，并在独立副本执行和核对导入。不要覆盖已有数据库，不需要执行表结构迁移。
3. 用当前源码构建 JAR，单独运行 `--app.demo-scenarios=true --app.jobs=false --spring.main.web-application-type=none`。
4. 核对数据和导入日志，再正常启动应用；正常启动不带导入开关。

示例为新增数据，使用老人编号 21001—21007，其余关联记录由数据库生成编号。预留老人编号或唯一业务字段发生冲突时，导入整批回滚。导入完成标记位于审计表，后续重复执行不覆盖用户修改，也不重新增加记录。不要手工删除标记或为重新导入清空业务表。

代码按档案与人员、订单履约、监测应急、补贴监管拆分在 `infrastructure/bootstrap/Scenario*.java`，统一由 `DemoScenarios` 开启事务。数据库外键、唯一约束、过程和触发器始终参与校验。

## 验证

枚举覆盖以 MySQL `information_schema` 中的基础表定义为准，共 30 个字段、100 个取值。过滤视图只展示符合条件的子集，例如待办视图不会包含已结案记录，因此不要求每个视图重复出现所有状态。

`DemoScenariosIntegrationTest` 验证所有枚举值有样例、原有行未被改写、重复执行不变、后段唯一冲突整批回滚、订单与资金证据一致，以及角色权限和真实办理操作。运行前连接独立的真实 MySQL 测试库。

`scripts/verify_scenarios.cjs` 用浏览器登录十个账号，读取角色菜单和业务详情，检查中文状态、手机布局及访问边界。该脚本不提交业务操作。照片与轮播由 `scripts/verify_media.cjs` 单独检查，新增无照片记录不影响已有头像对应关系。

2026 年 11 月 14 日本地验证记录见 [演示数据验证结果](../evidence/demo-scenarios.json)：170 项自动化测试通过，十个账号的 186 个列表入口检查通过。本机演示库有老人 39 位、护工 25 位、订单 82 笔、评价与投诉 38 条、补贴申报 28 笔、设备 26 台、体征记录 74 条、应急事件 32 条。数量对应该次导入后的本机数据；不同初始化批次及后续业务操作会改变数量。

课程材料中的监测阈值、补贴条件与金额仅用于演示，不能作为现实诊疗或政策依据。

## 数据命名

社区、机构和服务项目采用自然的业务名称，例如青禾社区、桂园社区、青禾养老服务中心、门诊就医陪同。初始化名称见 `src/main/resources/seed-labels.json`，人员姓名与头像对应关系见 `src/main/resources/static/demo-people.json`。这些均是课程使用的虚构资料，并不对应已运营机构或真实服务。

既有库可使用 `database/migrations/20261116_seed_names.sql` 更新内置名称。脚本只匹配已知来源和原占位值，保留手工修改的资料及原有编号、账号、授权范围、金额、业务状态。已确认的评估、服务凭证和审核日志遵守历史保护规则，保留原文；新初始化记录使用正常业务表述。内部来源标识、加密身份占位值和采样来源保留，以便追溯。监测阈值用于课程流程验证，不作为医疗判定标准。

登录页使用平台名称，工作台“关于平台”提供数据及图片来源说明。拨付功能登记业务凭证，不发起真实转账；定时采样功能保留模拟来源标识。
