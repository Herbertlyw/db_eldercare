# 从零理解这个项目

## 先理解系统在记录什么

把系统想成社区的服务台。管理员登记老人及评估结果，再制定照护计划；家属预约服务；管理员选择合适的护工；护工签到、服务、签退；家属确认后，这次服务才能作为补贴凭据。数据库要保存每一步的事实，并阻止不符合规则的操作。

一张表是一类事实，一行是一条记录。主键是记录的内部编号；外键指向另一条记录。例如订单的 elder_id 指向老人表，多个订单可以指向同一位老人。姓名可能重复、地址可能变化，所以不适合拿来当主键。

先在界面查看“老人档案”“能力评估”“照护计划”“服务订单”，对照编号找到联系。示例账号分属不同社区，家属只能看到自己关联的老人。数据库里的数据均为虚构，不是现实养老服务或医疗数据。

## 一次点击如何到达数据库

1. 浏览器中的 `static/app.js` 和 `static/completion.js` 收集输入，向 `/api/actions/order.assign` 发请求。
2. `interfaces/web/Api.java` 接收请求，`application/security/Auth.java` 根据登录令牌识别用户。
3. `application/CareService.java` 开启事务，将派单交给 `application/service/OrderService.java`。应用服务通过授权接口检查账号范围，通过仓储接口访问数据。
4. `infrastructure/persistence/JdbcOrderRepository.java` 通过 `Store.java` 使用 JDBC 执行带参数的 SQL，调用派单过程。
5. MySQL 检查约束和触发器，写入记录；全部成功才提交。

JDBC 是 Java 与数据库通信的接口。本项目用 Spring JdbcTemplate 减少连接、参数绑定和结果读取的重复代码。DAO 就是负责数据库读写的那一层，`Store` 是本项目的公共 DAO。

## 最需要讲清楚的四个概念

**事务**：改派需要释放旧名额、保留旧派单、占用新名额和写入新派单。这些动作是一个整体。新班次不合格时，不能留下“旧名额释放了但新名额没拿到”的半成品，因此要整体回滚。

**并发**：只剩一个名额时，两个人同时看到“还有一个”，并不代表两个人都能拿到。数据库必须协调这两个事务。本项目通过锁和带容量条件的更新处理竞争，测试实际同时发起两个事务验证只有一个成功。

**范式**：如果计划同时保存评估编号和老人编号，就可能出现“评估属于甲，计划却写乙”的矛盾。计划保存评估编号，再通过评估找到老人，可减少这种重复事实。数据库拥有单列 id 主键并不能自动证明第三范式。

**视图、过程和触发器**：视图封装常用查询；过程执行一组受控的数据库操作；触发器在写入或修改时自动校验或留痕。时间自己过去不会触发某张表的 UPDATE，因此评估到期、应急超时还需要定时检查，业务操作时也必须重新判断。

## 演示时如何解释限制

签到围栏是模拟输入，拨付是记录模拟凭证，体征阈值是课程数据，不能说已接入真实定位、支付或医疗设备。自动测试通过代表这些测试覆盖的行为成立，不代表所有现实情况都已验证。Windows 脚本提供数据库初始化和启动入口，但尚未在 Windows 实机验收。

每位成员先独立运行自己负责模块的一次成功操作和一次拒绝操作，再解释相关表、主外键、SQL、视图、过程、触发器和测试。个人报告应记录真实学习、修改和协作过程，不能把公共代码全部称为个人独立完成。

## 招聘 投诉与监管代码入口

招聘和培训看 `application/service/WorkforceService`，投诉看 `FeedbackService`，整改看 `GovernanceService`，设备和应急看 `MonitoringService`，申报补件看 `SubsidyService`。`application/ReadService` 提供查询入口，具体查询在 `infrastructure/query`。`Scope` 是授权接口，由 `infrastructure/security/JdbcScope` 实现。`application/support/Inputs` 检查输入，`infrastructure/scheduling` 下的 `Simulator` 和 `Jobs` 负责模拟采样与定时检查。

例如读投诉流程时，顺着 complaint.create、complaint.assign、complaint.reply、complaint.close 找到四次状态转换，再对照 complaint_log 查看每一步留了哪些记录。机构只能回复本机构承接订单的投诉；社区自办的投诉由管理员回复。

## 为什么这样分层

领域层保存“什么时候可以办”的规则，应用层安排“这一次怎么办”，基础设施层负责“怎样读写数据库”。例如投诉必须先受理、再回复、最后结案：规则在 `domain/feedback/Complaint`，步骤在 `application/service/FeedbackService`，SQL 在 `infrastructure/persistence/JdbcFeedbackRepository`。这样改 SQL 不需要改投诉状态规则，也能单独测试办理顺序。完整目录和开发约定见 [Java 架构与开发约定](Java架构与开发约定.md)。
