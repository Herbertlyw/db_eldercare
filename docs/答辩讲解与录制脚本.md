## 演示准备

启动应用前确认 MySQL 已运行，使用 .local/演示账号.txt 中的密码登录。演示样本按启动种子时的时间生成，若隔了较长时间，先检查计划与预约时间，不能把过期数据错误当成系统故障。录屏时不要展示配置中的数据库口令或字段密钥。

为了保留演示基线，拒绝案例可以直接运行；会改变订单的成功操作应在演示专用库或预先备份后进行。自动化测试使用 eldercare_test，避免污染展示库。

## 常见答辩问题

- 为什么不能直接更新订单中的护工编号？因为改派会丢失旧分配和原因，订单与派单必须一对多；有效派单唯一由生成列索引控制。
- 为什么有主键仍不能说满足第三范式？主键不排除非键属性间的函数依赖。本项目删除了计划中可由评估决定的老人字段、派单中可由班次决定的护工字段。
- 两个人同时派单怎样防超额？在事务中锁定相关对象，使用带 used_count < capacity 条件的更新，占位失败即抛出异常并整体回滚。
- 时间到期为何不能只写触发器？普通数据变更触发器不会因时钟前进而触发，需要定时任务主动调用过程，业务入口再即时校验。
- 设备换绑后为什么旧数据不会变？体征引用采集时的绑定历史编号，旧绑定仍保留原老人归属。
- 两种 SQL 为什么结果一样但执行计划不同？连接、EXISTS、相关子查询可表达相同业务语义，优化器根据索引和统计选择执行方式；必须先保证粒度一致，再比较计划。
- 为什么监管人员不能直接修正工时？原始服务事实与监管结论属于不同记录，监管应写审核或整改结果，不能无痕改写原始业务。
- 为什么用 Java JDBC？课程需要清楚展示 SQL、DAO 和事务边界，JdbcTemplate 减少连接资源管理样板，同时保留明确 SQL。
